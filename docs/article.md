# agent 缺的不是智力，是眼睛

**一个被数据逼着改了三次方向的项目复盘**

> 这不是一篇"我做了个 agent 项目"的文章。这是一篇"我本来想证明 A，结果被数据按着头改成了 B"的文章。
>
> 项目地址：https://github.com/haohaohao-cell/agent-silent-failure

---

## 一、起点：一个我自己劝自己放弃的选题

最开始我想做的是**明史 agent**。因为我喜欢历史，觉得这事有趣。

想法很具体：把《明史》《明实录》《国榷》灌进去，做一个能回答明代政治史问题的助手，每条回答都带出处。

我花了一个晚上写出方案，然后自己把它否了。理由是三个：

**第一，这个方向已经被做烂了。** "用 RAG 做某个垂直领域的问答"是当下最饱和的项目类型。通用大模型答明史已经有 70 分，你包一层检索可能 75 分——评委看不出差别。

**第二，它无法证伪。** 历史领域大量问题没有唯一答案（怎么评价张居正），模型可以随便发挥；而那些有唯一答案的问题（某年某职谁任），本质是数据库查询，不需要 agent。

**第三，也是最重要的：它证明不了任何事。** 项目做完，你只能说"我做了个东西"，说不出"我发现了什么"。

> 一个作品集项目的最低要求，不是"能跑"，而是**能说出一句别人没说过、且能被检验的话**。

后来我把这个判断固化成四条标准，用来筛所有候选选题：

1. **有客观评分** —— 对错不能靠你或评委"感觉"
2. **不是套壳** —— 核心难点不能一句话概括成"写 prompt + 调 API"
3. **10 秒能看懂** —— 不需要读 README 就知道在干什么
4. **能说出"我做到了别人做不到的哪一步"** —— 说不出来就是同质化

按这四条筛，明史问答一条都不过。

## 二、换方向：怎么选一个不被卷死的题

我列了五个 agent 方向，用上面四条标准打分。最后选的是：**给 agent 做故障注入，测它出错时知不知道**。

理由很功利：

- **它天然可量化。** 攻击成功率、静默失败率、需人工率——都是二值或数值指标，不需要论证"我的回答质量提高了"。
- **它稀缺。** 所有人都在做 agent，几乎没人做 agent 的失败测试。
- **它的结论能落地。** 不是"我做了个 demo"，而是"这样做会让 agent 少出错"。

但我当时押的核心假设是错的。这一点后面会讲。

## 三、第一原则：先让测量可信，再谈结论

动手第一件事不是写 agent，是写**沙盒**和**判定**。

**沙盒**：一个假业务世界——差旅报销审批，6 个工具，其中 `pay_out` 真的写库、真的扣预算。为什么不用聊天？因为只有**副作用**才能暴露"它到底做没做"。

**故障注入**：8 类故障，全部注入在**工具边界**——不碰模型，不碰框架内部。核心那类是"先执行、再抛超时"：服务端真的打了钱，客户端只是没收到确认。

这不是 bug，这是分布式系统的日常。

**判定**：6 条业务不变量 + 一个 2×2 矩阵。

|  | 任务做成了 | 任务没做成 |
|---|---|---|
| **agent 说成功** | 🟢 正常 | 🔴 **静默失败** |
| **agent 说失败** | 🟡 **虚假告警** | 🟠 响亮失败 |

左下角那格是后来意外发现的——钱付对了，agent 却以为错了。它在财务报表上完全隐形，但每一张虚假告警都是一张人工工单。

**还有一个决定我认为是整个项目最关键的**：先用一个**调用顺序写死的假 agent** 跑通全链路，不接 LLM。

因为 LLM 是不确定源。你要是直接把模型接进来，出了怪结果会分不清是 harness 有 bug 还是模型抽风，而这两件事的修法完全相反。假 agent 跑两遍必须一模一样，链路问题一眼暴露，而且不花一分钱 API 费。

## 四、假设之死 #1：agent 并不鲁莽

第一次接真模型（smolagents + deepseek-chat），结果很难看：

```
✗ get_receipts   SQLite objects created in a thread can only be used in that same thread
✗ get_employee   （同样的错）
✗ check_budget   （同样的错）
payments = 0
判定：🟢 正常
```

**它一笔都没打出去，判定却说"正常"。**

原因很简单：我所有不变量写的都是"不许做错"（不能付两次、不能超预算），而一个从头到尾失败的 agent，恰好什么都没做错。

这是整个项目最重要的一次教训：**"没有违规"不等于"做成了"。** 补了一条 `task_completed` 才堵住。这个洞如果没发现，后面所有数据都是废的。

修好之后，我等着看它盲目重试把钱打两遍。结果它这样做：

```
✗ pay_out       → 超时（但钱已扣）
· check_budget  → spent 从 10000 变成 13200
→ 结论："钱已经打出去了" → 不重试
```

它**回去查了预算**，发现钱扣了，于是主动放弃。

我的假设当场死亡。agent 不是鲁莽，它比我想的谨慎。

## 五、假设之死 #2：n=3 骗了我

我加了一个组合故障 `opaque_timeout`：付款超时，**而且复查时读到的还是旧快照**。让它没法验证。

这次它说了一句话，成了整份研究的钥匙：

> 「pay_out 为不可逆…为避免重复打款不能重试；**现有工具无法查询打款状态**，无法确认是否成功。」

缺口不是"不够谨慎"，是工具箱里少了一个查询工具。

于是我加了只读工具 `get_payment_status`，跑了个试点：对照组双打款 1/3，实验组 0/3。

看起来像强信号。我差点写进结论。

扩到 n=10 之后，对照组掉到 **1/10**。那 1/3 是运气。

> **n=3 不是样本，是轶事。** 试点只能用来判断"值不值得跑 n=10"。

## 六、假设之死 #3：一行没写的参数，让前面全白跑

实验做完，我发现同一份配置三次重复，双打款率分别是 0/10、4/10、2/10。

查下去：`smolagents` 的模型封装**如果不显式传 `temperature`，就用服务商默认值**——DeepSeek 是 1.0。

我从头到尾没传过。

所以前面所有实验，都是在温度 1.0 下采的，方差被采样噪声放大。方向还看得见，量级全不可信。

这类 bug 的可怕之处是**它不报错**。它只会给你一串看起来很合理的波动，然后你会把它当成现象去解释。

> **"昨天跑出来 0，今天跑出来 4" 不是发现，是没控制变量。**

修完之后，我把所有实验重跑了一遍，全部锁 `temperature=0`。

## 七、三个解释，排除两个

到这里，还能解释"agent 为什么停摆"的候选有三个：模型不够强、框架不对、缺少观测。

**换模型**（deepseek-chat vs deepseek-reasoner）：模型效应 **p = 1.00**。
而且推理模型更彻底——0 次双打款、0 次完成、10 次上报。它把"不犯错"做到极致，代价是一次活都不干。

**换框架**（手写 ReAct / smolagents 代码即行动 / LangGraph 显式状态图）：框架效应 **p = 1.00**。
三个框架的基线都是 10/10 需人工。

**加一个只读查询工具**：需人工从 9–10/10 掉到 **0/10**，p < 0.0001。

三个框架合计：**基线 30 次运行，0 次完成；加观测后 30 次，全部完成。**

> **提高模型能力，只会让它更谨慎地拒绝工作。要让它干活，得给它看得见的东西。**

## 八、反向发现：框架的重试会把偶发变成必然

结论出来之后我又想：如果"看不到结果"是病根，那有没有什么操作会让它更糟？

有的。**在框架层加无差别重试。**

LangGraph 支持给节点挂 `RetryPolicy`。我做了五个臂：

| 臂 | 双打款 | 静默失败 |
|---|---|---|
| 异常转消息（现状） | 0/10 | 0 |
| + 默认 RetryPolicy | 0/10 | 0 |
| + 无差别重试 | **10/10** | **10** |
| + 无差别重试 + 幂等 | 0/10 | 0 |

默认策略是安全的，而且理由很讲究：LangGraph 的默认重试判断对 `RuntimeError` 返回 False——它把这类错误当成"编程错误，重试没意义"，只重试连接错误、HTTP 5xx 这些基础设施错误。

但一旦你"顺手把重试打开"，**失败从概率变成必然**。不是 10%，是 100%。

因为：

- **模型的重试是判断**——它要读错误、权衡风险，所以有时放弃
- **框架的重试是机制**——无条件重跑节点，不读错误，不权衡

更糟的是它**删掉了观测信号**：模型压根不知道失败发生过，只看到重试后那次"成功"。

> 在基础设施层加个重试，看起来是提高成功率，实际是把偶发失败变成必然重复。

## 九、那些耗掉我半天的小坑

技术细节不值得单开一节，但这几个坑很有代表性：

**① pip 依赖解析器死循环。** CPU 跑满 500 秒，日志不动。用 `--no-deps` 逐个装，秒过。

**② `tempfile.mkdtemp` 在 Windows 上必然失败。** CPython 会把 `os.mkdir(path, 0o700)` 翻译成一个只给属主权限的 DACL，而受限进程不是那个属主。pip、venv、ensurepip 全卡在这。写了个 `sitecustomize.py` 把 mode 参数扔掉绕过。

**③ 中文断行。** PPT 里"人工工单"被拆成"人 / 工工单"，因为文本框宽度差了几像素。这类问题只能靠渲染出来看，靠代码推不出来。

**④ 字形替换。** `✗` 在 Consolas 里没有，渲染成斜体 x，和我手写的 `X` 混在一起很难看。全部换成 ASCII。

**⑤ 推送时的两道墙。** git 走 Windows schannel 报 `SEC_E_NO_CREDENTIALS`（换 OpenSSL 后端解决）；凭证助手依赖命名管道被沙箱拦（改用 token 直推）。这两个都是环境限制，不是代码问题——但如果你也在受限环境里做，会卡很久。

## 十、发布：让结论可检验

发布前我做了三件事：

**① 把原始数据纳入版本库。** 一个声称"需人工从 90% 降到 0"的仓库，如果拿不出原始数据，可信度会打折。六个实验的 JSON 加起来才 50KB。

**② 做了个 2×2 和一张干预对照表放在最前面。** 读者不需要读完就知道结论是什么。

**③ 主动写局限。** 比如"不变量本身有构造性局限，`amount_exact` 假设全额报销"、"每臂 n=10，细微信号测不出"。

> 主动披露方法的边界，比"我的系统全部抓到"可信一个量级。而且你迟早会被问到，不如自己先说。

## 十一、如果重来一次

**我会先写判定，再写 agent。** 判定错了，所有数据都是废的——这次差点就废了。

**我会更早扩样。** n=3 那个"强信号"浪费了我半天，还差点写进结论。

**我会把"温度"这类隐形默认值列成 checklist。** 采样参数、超时、重试、并发——这些默认值不写出来，实验就不成立。

**但有一件事我不会改**：先做一个笨但确定的假 agent。它让我在没有 LLM 干扰的情况下，把测量本身做对了。

## 附：给想做同类项目的人

如果你想做一个"能立住"的 agent 项目，我的建议是：

1. **先找指标，再找题目。** 先问"我能测什么"，比先问"我想做什么"更容易出成果。
2. **找一个有客观对错的任务。** 游戏、代码、SQL、有业务不变量的流程——都行。
3. **把失败当研究对象，而不是 bug。** 记录它怎么坏的，比展示它怎么好的信息量大得多。
4. **准备一个能自证的评测集。** 没有评测的 agent 项目，在技术面里会被问穿。
5. **允许自己的假设错。** 这个项目死了三个假设，但最后那句话比原计划的好得多。

> agent 缺的不是智力，是眼睛。
> 而重试，是把眼睛蒙上。
