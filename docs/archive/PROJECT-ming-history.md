# 明鉴 · 明代政治史 Agent

> 定位一句话：**一个能回答明代政治史问题、并且每条答案都能点开原文核对的 agent。**
> 形态：作品集项目（3–4 周可交付）

---

## 0. 先解决"宽而浅"的陷阱

"整个明代通史问答"是**竞争最激烈的形态**，也是作品集里最吃亏的形态：

- 通用大模型直接答明史已经有 70 分，你的 RAG 版可能 75 分，**评委看不出差别**。
- 通史 = 经济 + 文化 + 文学 + 社会 + 思想，语料量翻三倍，深度全塌。
- 一旦有人问"张居正一条鞭法具体怎么算"，你答不出，整个项目就掉档。

**修正方案：把"宽"重新定义。**

不是"所有学科都覆盖"，而是：

> **明代政治史四个维度全覆盖：人（人物）、官（职官）、事（事件）、战（军事）。**
> 对外说"明代政治史"，不说"明史"。这个表述比"明史"**更专业**，因为它证明你知道史学是有分科的。

这样语料只要四部书，2500 万字，**一个人一周能处理完**。宽度来自四维全覆盖 + 276 年时间轴，深度来自"任何一点都能下钻到原文"。

## 1. 产品形态：两层结构

这是本项目最重要的设计决策——**不要做成一个聊天框**。

### 第一层：浏览层（撑"广度"和第一眼观感）

- 明代 276 年**时间轴**（1368–1644），按年代排布关键事件
- **16 帝**世系 + 在位年号
- **事件卡片**：土木之变、靖难之役、大礼议、万历三大征、萨尔浒……
- **人物卡片**：生卒、字号、科第、历官、关联事件、史料出处
- **职官/地理**可后置

> 作用：让评委 10 秒内形成"这东西很完整"的印象。

### 第二层：问答层（撑"可信"和深度）

问任何问题，输出不是一段话，而是**带证据的回答**：

```
问题：土木之变时明军到底有多少人？

【结论】史料对兵力记载差异极大，无法给出确定数字。
        《明史》称"二十万"，《英宗实录》未载总数，
        《国榷》称"五十万"，现代研究多认为实际投入约十余万。

【引文】
① 《明史·英宗前纪》卷十：「……帅师二十万亲征。」
② 《国榷》卷二十七：「……号五十万。」
③ 《英宗实录》正统十四年八月：「……」

【分歧说明】明代军中"号"与实际员额差距可达数倍，
        《明史》与《国榷》的数字差异可能来自所据军籍不同。

【置信度】低（仅 3 条史料，且互相矛盾）
```

关键：**允许它说"不知道""有矛盾"**。这在历史领域是专业表现，不是能力缺陷。

## 2. 语料方案

| 书 | 规模 | 用途 | 优先级 |
|---|---|---|---|
| 《明史》 | 332 卷 / ~500 万字 | 主干叙事、人物传 | P0 |
| 《明实录》 | 2925 卷 / ~1600 万字 | 一手编年、校验 | P0 |
| 《国榷》 | 104 卷 | 异文对照（谈迁私修，保留清修史删改痕迹） | P1 |
| 《明史纪事本末》 | 80 卷 | 事件成篇，最适合做事件卡 | P1 |

**约 2500 万字。这个量级对检索系统是小数据**，BM25 单机完全扛得住，不需要向量数据库集群，不需要 GPU。这是"宽"可行的前提。

**版权红线**：中华书局点校本有版权，**不要直接抓**。用维基文库 / ctext / 殆知阁 / Kanripo 的公版电子文本，引用时标注来源。这条在 README 里要写清楚，是加分项（说明你有版权意识）。

**辅助数据**：
- CBDB（哈佛中国历代人物传记资料库）—— 明代人物覆盖极好，做人物消歧和对齐，能省两个月
- 明代年号表 / 闰月表 / 干支（自建一张小表即可）

## 3. Agent 架构（这是作品集的技术核心）

```
用户问题
   │
   ▼
[查询理解] ── 古文/现代词转换、别名→正名（"王阳明"→王守仁）
   │         判断问题类型：人物 / 事件 / 制度 / 数量 / 因果
   ▼
[查询规划] ── 拆成 2–4 个子查询，分配到不同语料
   │
   ▼
[混合检索] ── BM25（jieba + 单字兜底 + 2-gram）+ 向量召回 → rerank
   │
   ▼
[交叉验证] ── 拿到 A 书说法后，主动去 B 书找同一事件的记载
   │         检测数字/时间/人名/定性（"谋反"vs"擅权"）的冲突
   ▼
[引文校验] ── ★ 每条引文必须在语料中做规范化子串匹配
   │         匹配失败 → 重试 / 降级为"转述" / 拒答
   ▼
[时间归一] ── 年号+干支+闰月 → 公历区间（明用《大统历》）
   │
   ▼
[答案合成] ── 结论 + 引文 + 分歧说明 + 置信度
```

### 为什么这是 agent 而不是 RAG

必须能说出这句话：**"它不是检索一次就生成，而是会改写查询、多轮补检索、主动找反证、引文校验失败时自我修正、证据不足时拒答。"** 这五点每一点都要在代码里能找到对应函数。

## 4. 四个能写进简历的技术点

| # | 点 | 怎么说 | 工作量 |
|---|---|---|---|
| 1 | **引文强制校验** | "模型输出引文后做规范化子串匹配（去标点/异体字/繁简），失败即降级。幻觉率从 X 降到 Y。" | 1 天，收益最大 |
| 2 | **文言混合检索** | "文言文向量检索弱于 BM25，实测 jieba+单字+2gram 三路召回 + rerank 最优，出处召回 +N%。" | 3 天 |
| 3 | **纪年归一化** | "年号/干支/闰月/双轨纪年 → 公历区间，解决'万历十年'到底是哪年、闰月跨年等问题。" | 2 天 |
| 4 | **评测集** | "手工构建 100 题带 gold 出处，指标：引用准确率 / 出处召回率 / 无据断言率。" | 3 天，**面试官最看重** |

第 4 点是分水岭。**没有评测表的 agent 项目，在技术面里会被问穿。**

## 5. 评测方案（必须做，别省）

- **题目来源**：从《明史》本纪/列传里挑 100 个可验证断言，人工标注 gold 出处（卷次 + 原文片段）
- **三类题**：
  - 事实型（某年某职谁任）—— 考检索精度
  - 数量型（兵力、户数、年限）—— 考异文处理
  - 冲突型（史料互相矛盾）—— 考是否敢说"有分歧"
- **指标**：引用准确率（引文是否真实存在）、出处召回率（gold 是否被检索到）、无据断言率（说了但没引文的比例）
- **展示**：README 里放一张表，比任何 demo 视频都管用

## 6. 四周里程碑

| 周 | 交付 | 验收标准 |
|---|---|---|
| W1 | 语料 pipeline + 检索 | 输入"土木之变"，能返回四部书的相关原文段落，带卷次 |
| W2 | 问答 + 引文校验 | 10 个问题能答，每条引文可点击定位原文 |
| W3 | 浏览层 UI | 时间轴 + 事件卡 + 人物卡能跑通 |
| W4 | 评测 + 收尾 | 100 题评测表 + README + 一篇技术博客 |

**W1 结束就该能演示。** 如果 W1 做不出检索，说明语料方案有问题，立刻收缩到只做《明史》一部。

## 7. 90 秒 Demo 脚本（面试时按这个讲）

1. **10 秒**：打开首页 → 276 年时间轴 → "这是一个明代政治史的知识入口"
2. **30 秒**：点"土木之变" → 事件卡展示参战人物、时间线、四部史料的记载差异
3. **30 秒**：问"也先是不是只带了两万人" → 系统给出三本书的不同数字，**明确说"史料有分歧"**
4. **20 秒**：切到技术页 → 评测表 + 引文校验的实现

第 3 步是全场最关键的一步。**敢说"史料有分歧"，比给一个自信的错答案高一个档次。**

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 语料版权 | 只用公版电子文本，README 标注来源 |
| 文言分词差 | 三路召回 + rerank，别赌单一方案 |
| 幻觉 | 引文强制校验，匹配不上就拒答 |
| 范围失控 | 死守"政治史四维"，经济/文化/文学一律不做 |
| 没人用 | 作品集项目不需要真实用户，但需要**能自证准确** |
