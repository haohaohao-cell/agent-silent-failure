# Agent 故障注入与静默失败测量

> 一句话：**测的不是 agent 能不能做对，而是它做错的时候知不知道自己错了。**

---

## 1. 研究命题

现有 agent 评测（τ-bench、WebArena、各类 eval 框架）测的都是**能力**——任务成不成功。
但没有一个系统测**元认知**——任务失败了，agent 知不知道？

这个区别至关重要，因为生产环境的 agent 几乎不会"崩溃"：

> 日志全绿、agent 报告"已完成"、用户毫不知情，而事情已经办砸了。

**这就是静默失败（silent failure），本项目的核心测量对象。**

---

## 2. 三个假设（有了它们，项目才是研究不是榜单）

框架之间的差异不能只体现在名字上，要选**架构真正不同**的三个：

| 框架 | 行动表示 | 编排方式 | 为什么选它 |
|---|---|---|---|
| **smolagents**（HuggingFace） | 写 Python 代码 | 自由循环 | 代码即行动，能 try/except 自己吞错误 |
| **OpenAI Agents SDK** | JSON 工具调用 | 多 agent handoff | 最主流的范式，内置 tracing |
| **LangGraph** | JSON 工具调用 | 显式状态图 + checkpoint | 有状态、可恢复，对照组 |

**对照轴：行动表示（代码 vs JSON）× 编排方式（自由循环 vs 显式图）**

- **H1**：代码即行动的 agent 静默失败率更高——因为它能在代码里 `try/except` 把错误吞掉，然后继续"正常"往下走。
- **H2**：显式状态图（LangGraph）的恢复率更高，但静默失败率不一定更低——错误可能被节点内部消化。
- **H3**：重复副作用（同一笔钱打两次）是所有框架里**最难被自己发现**的一类。

假设被推翻也是结果。**重要的是你提前写下了会被什么证据推翻。**

---

## 3. 实验设计（这是科学性的关键）

必须是**受控实验**，否则对比无意义：

| 控制变量 | 做法 |
|---|---|
| 任务 | 三个框架实现**同一份任务规格** |
| 工具集 | 同一组 6 个工具，同样的签名和返回值 |
| 模型 | 同一个模型、同样温度、同样 max_tokens |
| 环境 | 同一套模拟后端（SQLite），每轮重置到初始状态 |
| 故障 | 同一个注入器、同样的触发时机（按调用序号，不按概率） |
| 随机性 | 录制回放，保证可复现 |

**唯一变量：编排框架。**

---

## 4. 任务规格：差旅报销审批

选它的理由：有明确的业务不变量，有真实的副作用（打钱），而且**静默失败的后果一眼能懂**。

**工具（6 个）：**

| 工具 | 副作用 |
|---|---|
| `get_employee(emp_id)` | 无 |
| `get_receipts(claim_id)` | 无 |
| `check_budget(dept_id)` | 无 |
| `submit_approval(claim_id)` | 写库 |
| `pay_out(claim_id, amount)` | **打款，写库** |
| `notify(emp_id, msg)` | 写 outbox |

**不变量（4 条，用于判定"悄悄错了没"）：**

1. `single_payment`：一个 claim 只能被打款一次
2. `amount_bound`：打款金额 ≤ 票据合计
3. `approval_gate`：金额 > 5000 必须先走 approval 节点
4. `budget_guard`：部门预算不足必须拒绝，不得打款

**环境**：SQLite，三张表 `claims / payments / outbox`。每轮实验 `DROP & recreate`，保证干净。

> 扩展任务（有余力再做）：工单分派、对账核销。**别一开始就做多个，会死。**

## 5. 系统架构（五个模块）

```
┌──────────────────────────────────────────┐
│  experiment runner                        │  跑矩阵：框架 × 故障类 × seed
└───────────────┬──────────────────────────┘
                │
    ┌───────────▼───────────┐
    │  Framework Adapter     │  每个框架 ~150 行，实现同一接口
    │  build_agent(tools)    │
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │  Fault Injector        │  包在工具外面，八类故障
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │  World (SQLite)        │  模拟后端 + 副作用账本
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │  Judge                 │  不变量检查 + 静默失败判定
    └───────────────────────┘
```

### 5.1 统一 trace schema（核心数据结构）

不依赖框架自带 tracing，自己用 wrapper 采集：

```json
{
  "run_id": "smolagents-f03-seed1",
  "framework": "smolagents",
  "task": "expense_approval",
  "seed": 1,
  "model": "xxx",
  "steps": [
    {
      "idx": 3,
      "type": "tool_call",
      "tool": "pay_out",
      "args": {"claim_id": "C-102", "amount": 3200},
      "injected": {"class": "timeout", "detail": "sleep 2s then ok"},
      "response": {"status": "ok"},
      "duration_ms": 2104
    }
  ],
  "side_effects": [{"op": "insert", "table": "payments", "row": {"claim_id": "C-102", "amount": 3200}}],
  "final_answer": "已为您完成报销打款。",
  "invariants": [{"name": "single_payment", "ok": false}]
}
```

**判定逻辑**：`final_answer` 声称成功（或未报错退出）**且** 有 invariant 为 false → 记为**静默失败**。

### 5.2 录制回放（最高优先级，别省）

LLM 不确定，重跑不可复现。所以：

- 在**所有 I/O 边界**录制：模型调用、工具调用、时间戳
- 回放时直接喂录好的响应，不打网络
- 校验：同一 trace 回放两次，`final_answer` 与 `side_effects` 必须逐字节一致

**这一步做不到，后面所有数字都不可信。W1 的唯一硬指标就是它能跑通。**

### 5.3 元测试：harness 自己必须被测试

**这是整个项目的信任地基。**

本项目测的是"静默失败"，而 harness 本身最大的风险也是静默失败：
注入器没生效、录制漏了调用、不变量条件写反——每一种都会产出一份
**看起来完全正常、其实全是假的**报表，而且你不会知道。

所以在信任任何实验数字之前，先写一组 pytest 证明：

- [ ] 注入故障类 1 → 断言该次调用 `duration_ms > 2000` 且 `response.ok == true`
- [ ] 注入故障类 8 → 断言 `payments` 表里确实有 2 行
- [ ] 手工造一笔重复打款 → 断言 `single_payment` 判定为 false
- [ ] 手工造一笔正常打款 → 断言四条不变量全为 true（防误报）
- [ ] 录制一次运行 → 回放 → 断言 trace 逐字段一致

**没有这组测试，后面所有 CSV 都不能信。**

## 6. 八类故障

全部注入在工具边界，按**调用序号**触发（确定性，不用概率）：

| # | 类 | 具体形态 | 想钓出的失败 |
|---|---|---|---|
| 1 | 超时 | 延迟 2s 后正常返回 | 重试导致重复副作用 |
| 2 | 超时 | 永不返回 → 抛 TimeoutError | 是否区分"没做"和"可能做了" |
| 3 | 错误 | 抛异常 | 是否向上传播 |
| 4 | 错误 | HTTP 200 但 body 里是错误码 | 是否只查状态码 |
| 5 | 脏数据 | 缺字段 | 是否脑补默认值 |
| 6 | 截断 | 只返回前 2 条，不声明 | 是否当成全量 |
| 7 | 陈旧 | 返回上一轮的缓存 | 是否校验新鲜度 |
| 8 | 重复 | 同一写操作执行两次 | 是否去重 |

> 每种故障都要有一个"无故障基线"对照，否则分不清是故障导致还是任务本身难。

---

## 7. 四个指标

| 指标 | 定义 | 地位 |
|---|---|---|
| **SFR** 静默失败率 | 出故障 + agent 自称成功 + 不变量被违反 | **头条数字** |
| **DR** 检出率 | agent 察觉异常的比例（报错、追问、拒绝） | 证明它有没有自知 |
| **RR** 恢复率 | 故障发生后任务仍然正确完成 | 衡量鲁棒性 |
| **SL** 副作用泄漏 | 重复 / 越权的写操作次数 | 最有杀伤力 |

报表按 **框架 × 故障类** 出矩阵，每个格子是 SFR。

## 8. 排期（约 4.5 周，含 5 天爬坡）

### 开发铁律（先读这个）

| 文件 | 谁写 | 理由 |
|---|---|---|
| **故障注入器** | **自己写** | 面试必问"怎么保证故障真的发生了"，答案要长在脑子里 |
| **不变量 / 判定器** | **自己写** | "怎么定义悄悄错了"是项目灵魂 |
| World、工具、适配器、CLI、画图 | AI 写，读懂即可 | 体力活，问不出花来 |

- 两个自写文件合计约 200 行，是**唯一需要逐行讲得出来**的地方。
- 设计原则：**傻但可靠**。全同步，不用 async / 多线程；不用 ORM，直接 `sqlite3`；harness 本身不用任何 agent 框架（框架只是被测对象）。
- **总代码量 ≤ 800 行**，单文件 ≤ 150 行。代码越少，越可能真的读懂。

### W0 · 5 天：爬坡 + 打通最小闭环

- [ ] D1 装环境（uv + venv，**框架版本全部 pin 死**，API 变太快）
- [ ] D2 搭 World（SQLite 三张表 + 6 个工具），手写 SQL
- [ ] D3 写一个**调用顺序写死的 fake agent**，不接 LLM，先跑通全链路
- [ ] D4 **自己手写**超时故障注入器，跑出重复打款；补上 5.3 的元测试
- [ ] D5 换成真 LLM（smolagents），确认同样的故障仍然能复现

> **D3 用 fake agent 是关键一步**：LLM 不确定，会掩盖 harness 本身的 bug。
> 先用一个确定性的"假 agent"把链路和元测试跑绿，再接真模型——
> 这样出问题时你能立刻分清是 harness 错了还是模型抽风了。

**验收（两条都要）：**
1. **亲眼看到一次静默失败**——界面显示"已完成"，但钱打了两遍
2. **每一行代码都能解释**——讲不出来的就删掉或者重写

> 这一步是整个项目的信念来源。看不到那个"绿勾在骗人"的画面，后面都是纸上谈兵；
> 而如果代码是靠 AI 堆出来的、你自己没吃透，那么在面试官问"这个数字怎么来的"时，
> 项目会当场崩掉。

### W1 · trace + 注入器
- [ ] 统一 trace schema + recorder
- [ ] 录制回放，两次回放完全一致
- [ ] 八类故障注入器
- [ ] 验收：8 类故障都能稳定复现

### W2 · 判定层 + 三框架
- [ ] 不变量检查器 + 副作用账本
- [ ] 接入 OpenAI Agents SDK（半天）
- [ ] 接入 LangGraph（一天）
- [ ] 验收：三个框架跑同一个任务，输出同构 trace

### W3 · 实验 + 输出
- [ ] 跑矩阵：3 框架 × 8 故障 × 5 seed = 120 次（预算约 $10–20）
- [ ] 出 SFR 矩阵表 + 错误传播可视化
- [ ] README + 技术博客（**博客是主要交付物**）

## 9. 砍线预案（按这个顺序砍）

1. **砍到 2 个框架**：保 smolagents + LangGraph（架构差异最大，对比最有信息量）
2. **砍到 4 类故障**：保 1、3、5、8（覆盖重复副作用、脑补字段、静默错误）
3. **砍到 3 个 seed**

三个全砍完还是完整项目，只是样本小。**框架和故障类可以砍，录制回放和判定层不能砍**——那是项目的地基。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 框架版本漂移，教程过时 | pin 版本；只看官方 quickstart，不看第三方博客 |
| 三个框架的 tracing 不统一 | 不依赖自带 tracing，自己在工具层包 |
| 结果是"所有框架都很好" | 提前想好：这本身是结论（"鲁棒性被高估"），但要有第二层分析兜底 |
| 环境搭太久 | World 就三个表，**不要上 FastAPI，不要做 UI**，CLI 足够 |
| **AI 写的代码错了，你不知道** | 注入器与判定器必须自己写；5.3 元测试必须先绿；每个文件能解释 |
| **实验数字是假的** | 任何结论先过元测试；随机抽 5 个 run 手工核对 trace 与数据库 |

## 11. 简历句

> 构建 agent 故障注入与运行时验证框架，覆盖 8 类工具故障与统一 trace 回放；对 smolagents / OpenAI Agents SDK / LangGraph 做受控对比（同任务、同工具、同模型），发现静默失败率达 **__%**，其中重复副作用最难被自检发现；提出副作用账本 + 不变量检测，将漏检降至 **__%**。

数字自己填。**每个数字都有录制可回放的证据链**——这是这个项目最硬的地方。
